# Master Security Agent v0.5 — Security Assessment Engine Design

Date: 2026-09-17  
Status: Approved for implementation  
Baseline: v0.4 observation-only assessment engine

## 1. Purpose

v0.5 improves the v0.4 engine without changing its safety boundary. The release makes scan execution more deterministic and resilient, expands safe web-security observations, correlates evidence into clearer findings, adds human-readable reporting, and improves the interactive CLI.

The implementation remains discovery-first and observation-only. It does not become an exploitation, credential-testing, password-cracking, persistence, or unrestricted network-scanning framework.

## 2. Safety and scope

Allowed behavior:

- Normalize and validate one explicitly supplied HTTP or HTTPS target.
- Resolve DNS and collect public transport metadata.
- Perform bounded unauthenticated GET requests.
- Follow a conservative redirect budget and record the sanitized redirect chain.
- Observe status, selected response headers, content type, TLS metadata, public HTML metadata, CORS-related response headers, and safe cookie attributes.
- Infer only evidence-backed public authentication-surface indicators.
- Correlate observations into descriptive findings with severity and confidence.
- Generate JSON and Markdown reports.
- Execute analysis modules concurrently against the already-collected sanitized network observation so modules never independently add network requests.

Not allowed in the default engine:

- Credentials, passwords, password testing, password cracking, credential stuffing, or login automation.
- Authentication submissions or arbitrary request bodies.
- User-supplied cookies, authorization headers, or token reuse.
- Endpoint wordlist discovery or brute force.
- Exploitation, bypass attempts, persistence, destructive actions, or address-range scanning.

## 3. Architecture

```text
CLI / Shell
    |
    v
ScanEngine
    |
    +--> TargetPolicy / Target
    |
    +--> bounded network collection (one explicit target)
    |       |
    |       +--> NetworkObservation
    |               +--> DNS
    |               +--> HTTP metadata
    |               +--> redirects
    |               +--> TLS metadata
    |               +--> public HTML
    |               +--> safe cookie metadata
    |
    +--> ModuleRegistry
    |       +--> AuthSurfaceModule
    |       +--> SecurityControlsModule
    |       +--> WebMetadataModule
    |
    +--> Evidence + Finding correlation
    |
    +--> ScanSession
    |
    +--> ReportWriter
            +--> JSON
            +--> Markdown
```

The network collection is deliberately centralized. Registered analysis modules receive the same sanitized `NetworkObservation` and do not perform their own HTTP requests. This keeps concurrency bounded to CPU/local parsing work after the network phase.

## 4. Core model improvements

The existing `Evidence`, `Finding`, `ModuleResult`, and `ScanSession` models remain compatible, but v0.5 adds explicit validation helpers and stable ordering rules.

### Evidence

Evidence continues to contain:

- id
- source module
- evidence type
- short descriptive value
- optional target URL
- safe structured metadata

Evidence values must never contain cookie values, authorization values, credentials, or request bodies.

### Findings

Severity remains `info`, `low`, `medium`, and `high`.

A finding gains:

- stable `id`
- title
- severity
- category
- summary
- evidence references
- recommendation
- confidence
- optional `metadata` for safe structured context

Findings are sorted deterministically by severity, category, and ID before reporting.

## 5. Target and execution policy

`TargetPolicy` remains the control point for scan safety and adds:

- maximum total analysis seconds
- maximum registered-module workers
- maximum redirect count
- maximum response bytes
- per-request timeout

Target validation continues to reject unsupported schemes, malformed URLs, embedded credentials, and targets outside the explicitly allowed HTTP/HTTPS policy.

The engine must not silently broaden target scope after DNS resolution or redirect handling. Redirects remain inside the declared HTTP/HTTPS protocol family and are bounded by policy.

## 6. Network observation improvements

`NetworkObservation` should expose safe structured values for:

- final normalized URL
- status code
- response headers after sanitization
- content type
- redirect chain
- resolved addresses
- TLS protocol/cipher/certificate validity metadata where available
- public HTML summary
- cookie security attributes
- CORS response observations
- a bounded response-size indicator

Do not store response bodies in the session.

Cookie parsing may retain attribute presence/value for `Secure`, `HttpOnly`, `SameSite`, `Path`, `Domain`, `Max-Age`, and `Expires`, but must not retain cookie names or values.

## 7. Security-control analysis

The existing security module is expanded to observe:

- HSTS
- CSP
- `X-Content-Type-Options`
- `Referrer-Policy`
- `Permissions-Policy`
- `X-Frame-Options`
- CSP `frame-ancestors`
- cookie `Secure`
- cookie `HttpOnly`
- cookie `SameSite`
- CORS response headers

The module should produce both control observations and conservative findings where evidence supports them. Absence of a header is not automatically a vulnerability: recommendations must make context explicit.

Examples:

- HTTPS observed → informational transport evidence.
- Missing HSTS on HTTPS → low-severity hardening observation.
- Missing `X-Content-Type-Options` → low-severity hardening observation.
- Wildcard `Access-Control-Allow-Origin: *` → informational/low observation depending on whether credentials are also allowed; never claim exploitability from headers alone.

## 8. Authentication-surface analysis

The authentication module gains broader passive indicators:

- OAuth/OIDC-like redirect markers.
- SAML-like redirect markers.
- `WWW-Authenticate` scheme extraction.
- public password-field metadata.
- identity-field metadata.
- login-oriented form actions.
- authentication-oriented page title.
- safe login-related response headers where present.
- stable evidence for multiple independent indicators.

The module reports candidate protocols, not confirmed backend identity-provider implementations.

## 9. Web metadata module

A new `WebMetadataModule` analyzes the already parsed public HTML and response headers without making additional requests.

It may observe:

- page title
- HTML form count and method/action metadata
- external script/style reference counts
- canonical URL metadata when already present in the bounded document
- security-relevant meta directives when directly present
- visible public technology hints from server/content-type headers

It must not automatically fetch referenced scripts, links, images, APIs, or forms.

## 10. Engine and concurrency

The engine keeps a single bounded network collection phase and then executes registered analysis modules through a bounded worker pool.

Requirements:

- Registration order remains deterministic.
- Results are reassembled in registry order regardless of completion timing.
- A failed module produces a failed `ModuleResult` and a session error without aborting other modules.
- The overall scan is considered complete when the network phase and all module futures have either completed or produced bounded timeout/error results.
- Module code receives only the immutable-by-convention target and shared read-only context.

Because modules are analysis-only and do not perform network requests, worker concurrency does not increase external request volume.

## 11. Findings correlation

The engine should provide a small correlation layer that deduplicates repeated evidence and ensures findings reference evidence IDs that exist in the session.

A finding may be created by a module or by a central correlation step. The first v0.5 implementation should keep correlation intentionally simple:

- merge duplicate evidence IDs
- remove duplicate findings by stable finding ID
- discard dangling evidence references
- sort evidence and findings deterministically

## 12. Reporting

JSON remains the machine-readable format.

Add Markdown with this structure:

```text
# Master Security Agent Report

Target
Scan summary
Findings
Evidence
Module results
Errors and warnings
```

Markdown findings should show severity, confidence, category, summary, evidence references, and recommendation. No sensitive values may appear.

## 13. CLI

Retain all v0.4 commands and improve the scan/report workflow:

```text
scan <url>
scan <url> --format json
scan <url> --format markdown
scan <url> --output report.json
modules
version
report <path>
```

`scan` stores the latest `ScanSession` in shell state. `report <path>` chooses JSON or Markdown from the destination extension (`.json`, `.md`, `.markdown`) while rejecting unsupported extensions with a clear message.

The shell's output should show:

- session ID
- target
- elapsed time
- module count and statuses
- evidence count
- findings grouped by severity
- error/warning counts

## 14. Testing

The v0.4 suite remains passing.

New tests cover:

- target policy limits
- network observation sanitization
- safe cookie parsing
- CORS observation
- web metadata analysis
- deterministic concurrent module ordering
- module timeout/failure isolation
- finding deduplication and evidence-reference validity
- JSON and Markdown report structures
- CLI option parsing and extension selection
- no additional network activity from analysis modules

Tests use in-process HTTP servers or direct observation fixtures. No test depends on a third-party website.

## 15. CI and packaging

CI should run on Python 3.11, 3.12, 3.13, and 3.14.

Add lint/type validation using lightweight tooling already compatible with the repository's standard-library-only runtime. Test dependencies may be installed through the existing `[test]` extra.

The package version moves to `0.5.0`, and the CLI banner, user agent, README, and report metadata use the same version.

## 16. Acceptance criteria

v0.5 is complete when:

1. The complete pytest suite passes on supported Python versions.
2. The interactive shell starts successfully.
3. `scan https://example.com/` performs one bounded network collection phase and completes analysis modules without credential submission.
4. Module results are deterministic in output order despite concurrent execution.
5. A single module failure does not abort the remaining modules.
6. JSON and Markdown reports contain identical substantive finding/evidence data.
7. Cookie values, cookie names, authorization values, credentials, tokens, and response bodies do not appear in reports.
8. Web metadata analysis makes no additional requests.
9. Security-control findings remain descriptive and conservative.
10. README documents installation, CLI usage, report formats, and the safety boundary.
11. CI validates tests and packaging for supported Python versions.
