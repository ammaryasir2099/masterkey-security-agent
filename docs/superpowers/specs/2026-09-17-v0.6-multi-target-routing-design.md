# Master Security Agent v0.6 — Multi-Target Routing and Modular Assessment Design

Date: 2026-09-17  
Status: Approved architecture; pending written-spec review before implementation  
Baseline: v0.5.0 observation-only security assessment engine

## 1. Purpose

v0.6 evolves Master Security Agent from a primarily website-oriented command flow into a routed, multi-target assessment platform. The user selects or identifies the target class, and the router dispatches the task to an independent target-specific module. Each module owns the algorithms, authorization requirements, observation adapters, and analysis appropriate to its target type while returning common evidence and finding objects to the shared reporting pipeline.

The release is intended to make the architecture scalable without turning the codebase into one large target-specific scanner. The existing v0.5 engine, evidence/finding models, correlation layer, reporting layer, and observation-only safety boundary remain the foundation.

## 2. Scope and safety boundary

The default v0.6 platform remains an authorized security-assessment tool. A target must be owned by the operator or explicitly authorized for assessment.

Allowed by the default architecture:

- Select a target type from an interactive menu or detect it from a supplied identifier/URL.
- Route the task to exactly one primary target module.
- Run target-specific passive discovery and analysis algorithms.
- Reuse the existing bounded, observation-oriented network layer for web targets.
- Use explicit authorized integrations for authenticated services, such as OAuth/API authorization or controlled test accounts.
- Produce common evidence, findings, confidence, recommendations, and reports.
- Keep target modules independently testable and independently replaceable.

Not part of the default v0.6 implementation:

- Credential theft or collection.
- Password cracking, credential stuffing, login automation, or MFA bypass.
- Session-cookie harvesting or replay.
- Exploitation, persistence, destructive actions, or unauthorized access.
- Broad Internet address-range scanning.
- Endpoint wordlist brute force as a default behavior.
- Circumventing provider security controls.
- Asking users to paste passwords, raw cookies, authorization tokens, or private session material into the tool.

Authenticated modules must use explicit authorization mechanisms and minimize the amount of sensitive data exposed to the assessment core.

## 3. Product model

The system is divided into five layers:

```text
Interactive Shell / CLI
        |
        v
Target Router
        |
        v
Target-Specific Assessment Module
        |
        v
Common Assessment Context
        |
        +--> Evidence
        +--> Findings
        +--> Correlation
        +--> Scan/Assessment Session
        +--> JSON / Markdown Reports
```

The router answers: "What type of target is this task about?"  
The target module answers: "How should this target class be assessed?"  
The common engine answers: "How is execution bounded, recorded, correlated, and reported?"

## 4. Target types

v0.6 defines a stable target-type enumeration and initial module set:

```text
WEBSITE
GMAIL
FACEBOOK
API
SERVER
```

The architecture must permit future additions without changing the core engine contract. Planned future target types may include mobile application, local application, cloud service, and other explicitly authorized platforms.

Target-type names are descriptive categories rather than guarantees about internal platform implementation.

## 5. Interactive shell and routing UX

The shell becomes the primary front door while retaining useful v0.5 commands such as `version`, `modules`, `scan`, and `report` during the transition.

The interactive menu should present approximately:

```text
========================================
       MASTER SECURITY AGENT
========================================

1. Website / Web Application
2. Gmail / Google Workspace
3. Facebook / Meta
4. API / REST Service
5. Server / Host
0. Exit

Select:
```

Selecting a module prompts for that module's target identifier. For example:

```text
1. Website / Web Application
Enter website URL:
>
```

The menu must validate input before dispatching it. Unknown or malformed targets must produce a clear error without terminating the shell.

Explicit user selection takes precedence over automatic detection.

## 6. Automatic target detection

A detector may infer a target type from an identifier when that is unambiguous enough to improve usability. Examples include a Gmail URL being recognized as GMAIL and an HTTP(S) application URL being recognized as WEBSITE.

Automatic detection must be conservative. It must not silently reinterpret an ambiguous username or domain as a specific third-party service without evidence.

The router should expose both:

```python
detect_target_type(value) -> TargetType | None
route(target_type, target_input) -> AssessmentModule
```

The shell should allow the operator to override detection explicitly.

## 7. Module contract

Every assessment module implements a common interface under `modules/base.py` or an equivalent stable location.

Conceptually:

```python
class AssessmentModule:
    name: str
    target_type: TargetType

    def validate_target(self, target_input: str, context: AssessmentContext) -> None:
        ...

    def assess(self, target_input: str, context: AssessmentContext) -> ModuleResult:
        ...
```

The exact implementation may use a protocol or abstract base class, but the contract must make module responsibilities and dependencies explicit.

Each module:

- Owns target-specific validation.
- Owns target-specific observation adapters.
- Owns target-specific analysis algorithms.
- Returns the shared `ModuleResult` representation.
- Does not modify another module's private state.
- Does not depend on another target module's internal implementation.

## 8. Common AssessmentContext

Introduce a shared context object that carries the minimum state needed by routing, modules, and reporting.

It should contain conceptually:

```text
target_type
target_input
normalized_target
authorization_scope
policy
observations
evidence
findings
metadata
session identifiers
```

Sensitive authorization material should not be copied into general-purpose context fields. Modules should receive opaque authorization handles or sanitized provider responses where possible.

The context is the integration boundary between independent modules and the common assessment/reporting pipeline.

## 9. Module registry

Extend the existing `ModuleRegistry` concept so modules can be registered by stable target type and name.

Example:

```text
website  -> WebsiteModule
gmail    -> GmailModule
facebook -> FacebookModule
api      -> ApiModule
server   -> ServerModule
```

The registry must support:

- Listing available modules.
- Looking up a module by target type.
- Stable registration order.
- Duplicate-name/type rejection.
- A clear readiness state for modules that require an external authorization integration.

The shell's `modules` command should display readiness without implying that a module can operate against arbitrary third-party targets.

## 10. Website module

The existing v0.5 website assessment capabilities become the first specialized module. The migration must preserve behavior while relocating target-specific responsibility out of the generic shell/engine.

Website assessment continues to use a single bounded network observation phase followed by local analysis modules.

Current capabilities to preserve:

- DNS resolution.
- HTTP/HTTPS status and metadata.
- Redirect observation within policy.
- TLS metadata where available.
- Public HTML metadata.
- Safe cookie security attributes.
- CORS response metadata.
- Security-control observations.
- Authentication-surface indicators.
- Web metadata.
- Evidence/finding correlation.

The website module must not broaden scope into unrestricted crawling or exploitation as part of v0.6.

## 11. Gmail / Google Workspace module

The Gmail module is a provider-specific assessment adapter, not a password-cracking component.

It has two conceptual paths:

### Public observation

Assess public web metadata where it is meaningful and safe.

### Authorized assessment

Use an explicitly authorized Google mechanism such as OAuth/API authorization or a controlled test account. The module must not request that users paste passwords or raw session cookies into the tool.

The initial v0.6 implementation should establish the module interface, target validation, authorization boundary, and test fixtures. Deep provider-specific security analysis can be delivered incrementally after the interface is stable.

The module should be able to report a distinct readiness/authorization state such as:

```text
READY
AUTHORIZATION_REQUIRED
NOT_CONFIGURED
```

without treating unavailable provider access as a scan failure of the whole application.

## 12. Facebook / Meta module

The Facebook/Meta module follows the same independent-module pattern.

The initial implementation should define:

- Authorized target identifier model.
- Public vs authorized assessment modes.
- Integration/authorization boundary.
- Provider-specific observation adapters.
- Common evidence/finding output.
- Isolated unit tests.

It must not implement credential theft, account takeover, bypasses, or unauthorized access.

## 13. API module

The API module provides a first-class path for REST/HTTP APIs. It should reuse safe HTTP observation primitives where appropriate while maintaining API-specific metadata and analysis.

Initial observations may include:

- TLS and transport metadata.
- HTTP status and content type.
- Security headers.
- CORS metadata.
- Authentication indicators.
- Error-response metadata where publicly exposed.
- Safe API-specific response metadata.

Authenticated API testing belongs to a later authorized mode and must use explicit authorization.

## 14. Server module

The server module is a distinct module because host/service assessment has different requirements from website assessment.

The first v0.6 scope is limited to the module contract and safe host metadata needed for future expansion. It must not automatically begin broad address-range scanning.

Future authorized server assessment can add controlled service discovery, version intelligence, configuration analysis, and vulnerability correlation under separate policies.

## 15. Execution model

The router selects one primary target module for an assessment. Inside that module, independent analysis stages may run concurrently when safe and useful.

The core engine remains responsible for:

- Policy enforcement.
- Session creation.
- Exception isolation.
- Time budgets.
- Result normalization.
- Correlation.
- Reporting.

Modules remain responsible for target-specific work.

The existing v0.5 property that analysis modules consume shared observations without independently multiplying external requests should be preserved for website assessment.

## 16. Authorization model

Introduce an explicit authorization state rather than inferring authorization from the target string.

Conceptually:

```text
UNVERIFIED
PUBLIC_ONLY
AUTHORIZED
```

A module that requires authenticated provider access must declare the required authorization state before performing that operation.

The core should record authorization mode in the assessment session without storing passwords, raw cookies, access tokens, or secrets.

## 17. Reporting model

Reports must include:

- Agent version.
- Assessment session identifier.
- Target type.
- Target identifier, sanitized where necessary.
- Authorization mode/state.
- Selected module.
- Module status.
- Evidence.
- Findings.
- Confidence.
- Recommendations.
- Errors and warnings.

The existing report sanitization rule remains mandatory: query strings/fragments and sensitive authentication material must not be retained in reports.

## 18. Error handling

Module failures must be isolated.

For example:

```text
Website module          SUCCESS
Gmail integration       AUTHORIZATION_REQUIRED
Facebook module         NOT_CONFIGURED
```

A provider integration being unavailable should not corrupt or abort unrelated modules or the shell.

Errors must be represented as structured module/session errors and shown clearly in the CLI and reports.

## 19. Testing strategy

The v0.5 regression suite must remain passing during migration.

New v0.6 tests should cover:

- Target-type enumeration.
- Explicit menu routing.
- Automatic detection and ambiguous-input rejection.
- Registry lookup and duplicate rejection.
- Module isolation.
- AssessmentContext serialization/safety.
- Authorization-state enforcement.
- Website behavior parity with v0.5.
- Gmail module validation and authorization-required state.
- Facebook module validation and authorization-required state.
- API module baseline behavior.
- Server module baseline behavior.
- Report inclusion of target type and authorization state.
- No passwords, raw cookies, access tokens, or other secrets retained in session/report objects.
- Shell remains interactive after target/module errors.

Provider modules should use mocks, fixtures, or local controlled endpoints in tests. Tests should not depend on third-party production accounts or live provider sessions.

## 21. Backward compatibility

Existing v0.5 command forms remain supported during v0.6:

```text
version
modules
scan <url>
report <path>
```

`scan <url>` remains a convenient direct website path. The interactive menu becomes the recommended entry point for multi-target assessment.

Existing `ScanSession`, `ModuleResult`, `Evidence`, `Finding`, and report consumers should remain compatible unless a change is necessary for target-type or authorization metadata.

## 22. Non-goals for v0.6

The following are explicitly deferred:

- Full Gmail account security auditing across all Google Workspace controls.
- Full Facebook account/platform security auditing.
- Automated credential attacks.
- Authentication bypass.
- Exploit execution.
- Unrestricted crawler/endpoint discovery.
- Comprehensive CVE intelligence.
- Runtime request blocking/protection enforcement.
- Portable bootable USB distribution.

Those capabilities can be evaluated as separate future projects once the modular routing foundation is stable.

## 23. Acceptance criteria

v0.6 is complete when:

1. The current 81-test v0.5 suite remains passing, plus the new v0.6 tests.
2. `modules` lists the registered target modules and their readiness states.
3. The interactive shell can route Website, Gmail, Facebook, API, and Server selections independently.
4. Explicit target selection overrides automatic detection.
5. Website assessment preserves v0.5's bounded observation-only behavior.
6. Gmail and Facebook modules have explicit authorization states and do not accept passwords/raw cookies as general input.
7. API and Server modules have isolated baseline implementations.
8. A failure or missing authorization in one module does not abort the shell or unrelated modules.
9. Common evidence/finding/reporting interfaces work across modules.
10. Reports record target type and authorization state while excluding secrets.
11. Each module can be unit-tested without requiring another provider module's implementation.
12. The architecture permits adding a new target module without rewriting the core engine.

## 24. Implementation sequencing

Implementation should proceed in small increments:

1. Add target-type and authorization models.
2. Extract the common module interface and context.
3. Extend the registry for target-aware routing.
4. Add the router and interactive menu.
5. Migrate the existing website functionality with compatibility tests.
6. Add isolated API and Server baseline modules.
7. Add Gmail and Facebook provider module skeletons with authorization-required states.
8. Update reporting and CLI output.
9. Add comprehensive router/module regression tests.
10. Run full tests, Ruff, package build, and real local end-to-end menu/module tests.

No implementation step should weaken the current observation-only boundary while v0.6 foundations are being introduced.
