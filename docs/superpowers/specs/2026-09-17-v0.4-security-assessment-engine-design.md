# Master Security Agent v0.4 — Security Assessment Engine Design

Date: 2026-09-17  
Status: Proposed for implementation after review  
Baseline: v0.3 discovery-first agent

## 1. Purpose

v0.4 turns the current discovery prototype into a modular, evidence-driven security assessment engine. The agent will execute a bounded set of unauthenticated, non-destructive discovery and security-observation modules against an explicitly supplied HTTP(S) target, correlate the observations into structured findings, and produce reproducible terminal and JSON output.

The v0.3 modules remain the foundation. v0.4 adds a small orchestration layer, a stable finding model, stronger authentication-surface evidence, and a registry so future modules can be added without rewriting the shell.

## 2. Safety and scope

The default engine is observation-only.

Allowed v0.4 behavior:

- Normalize and validate an explicitly supplied HTTP or HTTPS URL.
- Resolve DNS and collect public network metadata.
- Perform bounded unauthenticated HTTP(S) GET requests.
- Follow and record normal redirects.
- Observe response status, content type, selected headers, TLS metadata, and public HTML metadata.
- Parse authentication-related indicators from public responses.
- Parse `Set-Cookie` attributes while never storing cookie values.
- Generate descriptive findings tied to concrete evidence.

Not part of v0.4:

- Credential collection, password testing, password cracking, credential stuffing, or login automation.
- Form submission or authentication requests.
- Session-cookie reuse or token harvesting.
- Endpoint brute-force/discovery wordlists.
- Exploitation, bypasses, persistence, or destructive actions.
- Scanning arbitrary address ranges from the default engine.

Credential-compromise or active exploitation experiments remain isolated to controlled systems owned or explicitly authorized for testing.

```text
CLI / Shell

ScanEngine

    +--> ModuleRegistry
    |       +--> LocalDiscovery
    |       +--> NetworkDiscovery
    |       +--> PublicHTMLDiscovery
    |       +--> AuthenticationSurface
    |       +--> SecurityControls
    |
    +--> EvidenceStore
    |
    +--> FindingEngine
    |
    +--> ReportWriter
```

### 3.1 Core packages

`src/masterkey_agent/core/`

- `target.py` — normalized target and policy validation.
- `engine.py` — execution orchestration and scan session lifecycle.
- `registry.py` — deterministic module registration and execution order.
- `findings.py` — typed finding/severity/evidence models.
- `session.py` — serializable scan-session state.

`src/masterkey_agent/discovery/`

Existing modules remain reusable. New logic should be placed into focused modules rather than appended to `shell.py`.

`src/masterkey_agent/report.py`

Extend JSON reporting to support a scan session while retaining compatibility with the v0.3 state shape where practical.

## 4. Module contract

Each assessment module should expose a small deterministic interface:

```python
class DiscoveryModule(Protocol):
    name: str

    def run(self, target: Target, context: ScanContext) -> ModuleResult:
        ...
```

`ModuleResult` contains:

- module name
- success/failure state
- evidence records
- optional observations
- findings generated by that module
- bounded error information

Modules must not mutate unrelated session state directly. The engine combines results into the session.

## 5. Target model and policy

`Target` contains:

- original input
- normalized URL
- scheme
- hostname
- optional port
- path

Target validation will reject unsupported schemes and malformed URLs before network modules run.

The default policy is explicit and conservative:

- HTTP and HTTPS only.
- GET-based public inspection only.
- No credential-bearing requests.
- No custom cookies supplied by the user.
- No request body submission.
- Bounded response size.
- Bounded redirect count.
- Clear timeout.

The policy object is designed so future lab-only policies can be implemented separately without weakening the default mode.

## 6. Evidence model

Evidence is the fundamental unit used by findings and reports.

Each evidence record should identify:

- source module
- evidence type
- short descriptive value
- target URL when applicable
- optional structured metadata

Sensitive values must be excluded or redacted before evidence reaches the session/report.

Examples:

- `transport.https`
- `header.hsts`
- `header.csp`
- `auth.password_field`
- `auth.oauth_redirect_marker`
- `auth.www_authenticate`
- `cookie.secure_attribute`
- `cookie.httponly_attribute`
- `cookie.samesite_attribute`

## 7. Finding model

A finding is descriptive and evidence-backed rather than a claim that a target is compromised.

Fields:

- `id`
- `title`
- `severity`: `info`, `low`, `medium`, `high`
- `category`
- `summary`
- `evidence_refs`
- `recommendation`
- `confidence`

The initial severity set is intentionally conservative. The engine should not label a missing control as a confirmed vulnerability unless the evidence actually supports that conclusion.

Initial categories:

- `transport`
- `authentication`
- `security_headers`
- `cookies`
- `content`
- `availability`

## 8. Authentication-surface analysis

The authentication analyzer will expand v0.3's mapper without attempting authentication.

Evidence sources:

1. Redirect locations containing recognizable OAuth/OIDC or SAML markers.
2. `WWW-Authenticate` challenges and their declared schemes.
3. Public form metadata containing username/email/password indicators.
4. Authentication-oriented form actions.
5. Authentication-oriented page titles.
6. Public HTML references to recognizable identity/login endpoints or protocol markers, without fetching undiscovered links automatically.
7. Authentication-related headers where safely observable.

Authentication confidence remains an evidence count/quality indicator only. It must not be presented as proof that a particular authentication protocol is actually deployed internally.

## 9. Security-control observations

v0.4 should add structured observation of selected controls:

- HSTS
- CSP
- X-Content-Type-Options
- Referrer-Policy
- Permissions-Policy
- X-Frame-Options or CSP frame-ancestors
- cookie `Secure`
- cookie `HttpOnly`
- cookie `SameSite`

Cookie values are never retained. Only attribute presence and safe metadata are stored.

Where a control is absent, the engine records an observation first; any finding severity is conservative and tied to context.

## 10. Network observations

The existing network inspector remains responsible for the bounded transport operation.

v0.4 should preserve:

- DNS resolution
- HTTP status
- redirect chain
- content type
- selected response headers
- TLS version/cipher/certificate metadata
- bounded public HTML parsing

The network layer should expose sanitized structured data to higher layers and remain free of presentation logic.

## 11. Scan session

`ScanSession` is the single object representing one run.

It contains:

- session identifier
- start/end timestamps
- target
- policy summary
- module results
- evidence
- findings
- errors/warnings
- tool version

The session must be JSON serializable and deterministic enough for tests to compare structure without depending on real-world dynamic timestamps.

## 12. CLI behavior

Retain the interactive shell for compatibility, but add an engine-backed command:

```text
scan <url>
```

Expected behavior:

1. Validate target.
2. Create scan session.
3. Run registered modules in deterministic order.
4. Print target summary.
5. Print module status.
6. Print evidence-backed findings.
7. Store session in shell state for `report <path>`.

Existing v0.3 commands remain available during the transition.

## 13. Reporting

JSON reports should contain:

```json
{
  "agent_version": "0.4.0",
  "session": {},
  "target": {},
  "modules": [],
  "evidence": [],
  "findings": [],
  "errors": [],
  "warnings": []
}
```

No credentials, cookies, authorization values, tokens, or request bodies may appear in reports.

## 14. Error handling

Network/module failures are isolated. A failure in one module must not corrupt the session or prevent unrelated safe modules from completing.

Each error should identify:

- module
- stage
- safe error message

The engine should distinguish:

- invalid target
- DNS failure
- connection failure
- timeout
- unsupported content
- parser failure
- unexpected module failure

## 15. Testing strategy

The v0.3 suite must remain passing.

v0.4 adds unit tests for:

- target normalization/validation
- module registry ordering
- engine orchestration
- session serialization
- finding serialization
- evidence redaction
- cookie attribute parsing without cookie values
- security-control observations
- authentication-surface correlation
- partial module failure handling
- `scan` shell dispatch
- JSON report structure

Network behavior should primarily use local in-process test servers and fixtures so tests are reproducible and do not depend on third-party websites.

## 16. Acceptance criteria

v0.4 is considered functionally complete when:

1. `pytest -q` passes all existing and new tests.
2. `python -m masterkey_agent.shell` starts successfully.
3. `scan https://example.com/` completes without credentials or form submission.
4. A scan session can be written to JSON.
5. Authentication evidence and security-control evidence are separated.
6. Cookie values never appear in memory models exposed to reporting/tests.
7. One failing module does not abort the entire scan session.
8. New modules can be registered without modifying the core execution loop.
9. The README documents installation, commands, safety boundary, and sample output.
10. The implementation remains suitable as the foundation for a later portable/USB deployment layer.

## 17. Evolution beyond v0.4

Later versions may add isolated adapters for authorized lab tooling, richer local-platform discovery, a plugin/package format, and eventually a bootable portable environment. Those additions should consume the stable scan-session/evidence interfaces rather than coupling directly to the interactive shell.
